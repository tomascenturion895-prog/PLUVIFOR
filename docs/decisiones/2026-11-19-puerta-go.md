## Actualización de las 11:15: Go ya lee la base

Después de la primera versión de este documento, el equipo indicó que **Python procesa los datos y Go hace todo el trabajo de consultas por rapidez**. Se escribió el adaptador de lectura (`internal/sqlstore`, solo `database/sql`, base abierta en solo lectura) y se probó:

| Pregunta | Respuesta |
|---|---|
| ¿Go lee la base real? | **Sí**, en una base SQLite de verdad: las 47 consultas de paridad dan lo mismo que Python (`TestParidadConPythonDesdeSQLite`). Rompiendo el SQL a propósito (un hueco como 0, otro orden) la prueba falla |
| ¿Qué falta? | Un paso con acceso normal a los módulos de Go: `go get github.com/ncruces/go-sqlite3@v0.25.0 && go mod tidy`, y commitear `go.mod` y `go.sum` (desde el entorno de desarrollo no se puede generar un `go.sum` verificable). Pasos exactos en `apps/api-go/README.md` |
| ¿Qué pasa si no se hace? | Nada se rompe: sin driver, Go arranca igual y reenvía a Python con el mismo contrato |
| ¿Es más rápido? | Sí, medido con la base de demostración: entre 1,7 y 5,5 veces menos tiempo por pedido y entre 4 y 10 veces más pedidos por segundo con 8 conexiones. Es una medición chica, no una prueba de carga |

**Resultado para la puerta:** con el paso del driver hecho, **Go sigue como API principal** y sirve estaciones y `GET /api/rainfall` por sí mismo. Mientras tanto, o si el paso no llega antes del 23/11, esas rutas salen de Python con el mismo contrato (sin cambios para la interfaz). Las demás rutas (comparador, acumulados, parte, importación, salud de la red, reportes de campo) siguen en Python hasta portarlas de a una.

## Qué falta decidir al equipo

- Confirmar el driver (`ncruces/go-sqlite3`; la alternativa equivalente es `modernc.org/sqlite`) y correr el paso de arriba.
- Con Go adelante, poner `RATE_LIMIT_PER_MINUTE=0` en Python (Go limita por cliente) y no exponer Python a Internet.
- Anotar la decisión con fecha y hora en un comentario de SCRUM-87.
